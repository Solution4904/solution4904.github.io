# 💡 [22] Looper, Handler,, HandlerThread
- 스레드를 관리하고 비동기 통신을 처리하기 위해 함께 작동하는 컴포넌트.
- 백그라운드 스레드에서 작업을 수행하면서 UI 업데이트를 위해 메인 스레드와 상호작용하기 위한 필수적인 컴포넌트.


> - Looper
>   - 스레드를 살아있게 유지하여 메시지, 작업 큐를 순차적으로 처리하는 안드로이드 스레딩 모델의 일부.

> - Handler
>   - 스레드의 메시지 큐 내에서 메시지나 작업을 보내고 처리. Looper와 함께 작동.

> - HandlerThread
>   - Looper가 내장된 특수한 Thread.
>   - 작업 또는 메시지 큐를 처리할 수 있는 백그라운드 스레드를 생성하는 과정을 단순화.


### 📑 사용 사례
- Looper : 연속적인 메시지 큐를 관리.
- Handler : 스레드 간 통신. (UI 업데이트)
- HanlerThread : 전용 스레드가 필요한 데이터 처리, 네트워크 요청과 같은 백그라운드 작업.

# 💡 [24] Exceptions
- 예외를 추적하고 앱에서 발생하는 문제를 효과적으로 진단하고 해결하는데 중요.


> - Logcat
>   - 로그를 보고 예외를 추적하는 기본적인 도구

> - try-catch
>   - 예외를 제어된 방식으로 처리하고 크래시 방지

> - 전역 예외 핸들러 (Thread.setDefaultUncaughtExceptionHandler)
>   - 앱 전체에서 처리되지 않은 예외를 포착하는데 도움
>   - 중앙 집중식 오류 보고, 로딩에 유용

> - Firebase Crashlytics
>   - 프로덕션 환경에서 예외를 추적하는 도구.
>   - 처리되지 않은 예외를 자동으로 기록, 스택 트레이스, 기기 상태, 사용자 정보의 보고서를 제공

> - Breakpoints
>   - 코드 실행을 일시 중지하고 점진적으로 검사.
>   - 변수, 메소드 호출, 예외 스택 트레이스를 상세하게 탐색 가능.

> - 버그 리포트 캡처
>   - 개발자 옵션
>   - Android Emulator
>   - Android Debug Bridge

# 💡 [25] 빌드 변형(Build Variants)? 플레이버(Flavors)?
- 단일 코드베이스에서 앱의 다양한 버전을 생성하는 유연한 방법 제공.


> - 빌드 변형 (Build Variants)
>   - 특정 빌드 타입과 제품 플레이버를 결합한 결과.
>   - 디버그 (Debug) : 개발 중에 사용되는 빌드 구성.
>   -  릴리스 (Release) : 배포에 최적화된 구성.

> - 제품 플레이버 (Product Flavors)
>   -  유료/무료 버전, us/ko과 같은 다양한 변형 정의 가능.


### 📑 빌드 변형 및 플레이버 사용의 이점
1. 효율적인 구성 : 중복 코드를 줄이고 단일 코드베이스에서 여러 빌드 처리 가능
2. 커스텀 동작 : 유료 버전에서 프리미엄 기능을 활성화하거나 디버그와 릴리스 빌드에서 각각 다른 API를 사용하는 등 앱 동작을 맞춤 설정할 수 있음.
3. 자동화 : Gradle은 빌드 변형에 따라 APK 서명, 최적화, 난독화 같은 작업을 자동화.

# 💡 [26] 접근성 보장

>   - UI 컴포넌트에 텍스트 레이블을 제공 (android:contentDescription)
> - 동적 글꼴 크기 지원
>   - 자동으로 크기가 조정되도록 텍스트 크기에는 sp 단위 사용
> - 포커스 관리 및 탐색

>   - 키보드 및 D-패드 사용자를 위한 논리적인 탐색 경로 정의 (android:nextFocusDown, android:nextFocusUp)

>   - 텍스트와 배경색간에 충분한 대비를 제공
> - 커스텀 뷰 및 접근성
>   - AccessibilityDelegate를 구현하여 스크린 리더가 커스텀 UI 컴포넌트와 상호 작용하는 방식을 정의할 수 있음.
> - 접근성 테스트
>   - Accessibility Scanner, Layout Insoectir와 같은 도구를 사용하여 접근성 문제를 식별하고 수정.

# 💡 [27] 안드로이드 파일 시스템
- 안드로이드 기기에서 데이터 저장을 관리하고 구성하는 구조화된 환경
- 앱과 사용자가 파일을 효율적으로 저장, 검색, 관리할 수 있도록 함.
- 리눅스 파일 시스템 아키텍처 위에 구축되어 엄격한 보안 및 권한 모델을 준수하면서 앱을 위한 비공개 및 공유 저장 공간을 모두 제공.


> - 주요 구성 요소
>   - System Partition(/system) : 안드로이드 프레임워크 라이브러리, 시스템 앱 및 구성파일을 포함한 핵심 운영 체제 파일이 들어있음. 우발적이거나 악의적인 수정을 방지하기 위해 일반 사용자 및 앱에 대해 읽기 전용.
>   - Data Partition(/data) : 데이터베이스, SharedPreferences 미 사용자가 생성한 파일을 포함한 앱 별 데이터가 저장. 각 앱으 해당 앱만 접근할 수 있는 비공개 디렉토리를 가지므로 데이터 보안이 보장.
>   - Cache Partition(/cache) : 시스템 업데이트, 기기 재시작 시 유지할 필요가 없는 캐시된 파일과 같은 임시 데이터 저장에 사용.
>   - External Storage(/sdcard, /storage) : 여러 앱에서 접근할 수 있는 공유 공간 제공. 이미지, 비디오, 문서와 같은 미디어 파일에 자주 사용.
>   - Tempnary Files(/tmp) : 앱 실행 중 임시 파일을 저장.일반적으로 앱이나 시스템이 재시작될 때 지워짐.


> - 파일 접근
>   - 내부 저장소(Internal Storage) : 앱 샌드반스 내의 비공개 저장 공간. 해당 앱만 접근 가능. 민감하거나 앱 별 데이터 저장에 사용.
>   - 외부 저장소(External Storage) : 여러 앱에서 접근할 수 있는 공유 저장 공간. 사용자가 앱 외부에서 접근할 것으로 예상되는 사용자 생성 콘텐츠 또는 미디어 저장에 사용.


> - 파일 권한 및 보안
>   - 비공개 앱 데이터 : 앱의 내부 저장소에 저장된 파일은 비공개. 해당 앱만 접근 가능
>   - 공유 파일 : 앱 간에 파일을 공유하려면 외부 저장소나 적절한 권한이 있는 ContentProvider 사용.
>   - 범위 지정 저장소 : 안드로이드 10에서 도입. 공유 저장소에 대한 직접 접근을 제한하여 앱ㅇ ㅣMediaStore 또는 SAF(Storage Access Framework) API를 사용하도록 요구.

# 💡 [28] 안드로이드 런타임(ART), Dalvik, Dex 컴파일러
- 안드로이드 앱은 기기에서 실행되기 위헤 고유한 런타임 환경과 컴파일 프로세스에 의존.
- ART, Dalvik, Dex 컴파일러는 앱의 성능, 메모리 효율성, 기기와의 호환성을 위해 최적화되도록 보장함.


> - ART (5.0부터 디폴트로 사용 중)
>   - 개선된 성능 : AOT(Ahead-of-Time)컴파일은 최적화된 기계 코드를 생성하여 런타임 오버헤드를 줄임.
>   - 가비지 컬렉션 : 개선된 가비지 컬렉션 기술이 도입되었음.
>   - 디버깅/프로파일링 지원 : 상세한 스택 트레이스 및 메모리 사용량 분석 도구 제공.

> - Dalvik (ART 이전에 사용되었음)
>   - 컴팩트한 바이트코드 : 낮은 메모리 사용량과 빠른 실행을 위해 최적화된 Dalvik Executable 파일을 사용.
>   - 레지스터 기반 VM : 스택 기반이 아닌 레지스터 기반이므로 명령어 효율성이 향상.

> - Dex 컴파일러 (안드로이드 빌드 시스템에 통합됨)
>   - 멀티덱스 지원 : 바이트코드를 여러 .dex파일로 분할 지원
>   - 바이트코드 최적화 : 더 나은 메모리 사용량과 실행 성능을 위해 바이트코드를 최적화.

# 💡 [29] APK, AAB
> - APK (Android Package)
>   - 앱이 기기에서 작동하는 데 필요한 모든 리소스, 코드, 메타데이터를 포함하는 완전하고 즉시 설치 가능한 패키지.
>   - 모든 기기의 구성에 대한 리소스를 포함하고 있어서 사용자의 기기와 관련 없는 리소스를 포함하게 되어 파일 크기가 큼.
>   - 공식 앱 스토어 외부에서 공유하거나 사이드로딩할 수 있음.

> - AAB (Android App Bundle)
>   - 설치 가능 형식이 아닌 게시 포멧. Google Play에 업로드하면 이를 개별 기기에 맞게 최적화된 APK로 처리.
>   -  모듈식으로 다른 구성에 대한 리소스와 코드를 별개의 번들로 분리. 다운로드 시점에 기기 별로 필요한 리소스와 코드만 전달하여 APK를 생성해서 앱 크기를 줄임.
>   - Google Play 서버 측에서 처리되므로 직접 설치 불가능. 때문에 bundletool없이 사용자에게 직접 배포, 설치 유도 불가.


### 📑 주요 차이점
||APK|AAB|
|---|---|---|
|목적 및 구조|모든 구성에 대한 모든 리소스와 코드를 포함하는 완전한 패키지|기기 별 APK를 생성하는 모듈식 게시 형식|
|파일 크기|큼|작음|
|배포|직접 공유, 사이드로딩O|Google Play, 사이드로딩X|
|관리|리소스와 구성 수동 관리|Google Play에 위임|
|도구 및 호환성|모든 안드로이드 기기 및 앱 스토어 지원|Google Play or bundletool|

# 💡 [30] R8 최적화
- 안드로이드 빌드 프로세스에서 APK 또는 AAB의 크기를 줄이고 런타임 성능을 향상시키기 위해 사용되는 코드 축소 및 최적화 도구.
- 안드로이드 빌드 시스템에 통합되어 프로가드를 대체함.


### 📑 작동 방식
- 코드 축소 : 코드베이스에서 사용되지 않는 클래스, 메소드, 필드, 속성을 제거.
- 최적화 : 메소드 인라이닝, 중복 코드 제거, 동일 코드 블록 병합으로 코드를 단순화하고 재구성.
- 난독화 : 클래스, 메소드, 필드 이름을 모호하게 만들어 리버스 엔지니어링을 어렵게 함.
- 리소스 최적화 : 사용되지 않는 리소스를 제거.


### 📑 주요 특징
- 죽은 코드 제거 : 코드베이스를 분석해서 앱에서 도달할 수 없거나 사용되지 않는 코드 식별&제거
- 인라이닝 : 짧은 메소드나 함수를 호출자쪽에서 직접 인라인하여 메소드 호출 오버헤드를 줄이고 런타임 성능 향상.
- 클래스 병합 : 유사한 클래스나 인터페이스를 하나로 결합하여 메모리 공간을 줄이고 효율성 향상.
- 상수 폴딩 및 전파 : 표현식으로 단순화하고 변수를 가능한 경우 해당 상수 값으로 대체.
- 난독화 : 의미 있는 이름을 더 짧고 덜 설명적인 이름으로 대체하여 앱 크기를 줄이고 리버스 엔지니어링을 더 어럽게 만듦.


### 📑 구성
- 프로가드 규칙을 동일하게 사용
> - 리플렉션을 위한 코드 보존
> - 서드파티 라이브러리 제외


### 📑 장점
- 긴밀한 통합 : 안드로이드 빌드 시스템에 내장되어 있어 일반적인 프로가드 규칙 외에 추가 설정 X
- 향상된 효율성 : 축소, 최적화, 난독화를 단일 패스로 결합.
- 앱 크기 감소 : 사용되지 않는 리소스 제거
